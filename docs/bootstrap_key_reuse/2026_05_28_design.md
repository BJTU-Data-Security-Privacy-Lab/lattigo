1. Problem essence

这个问题的本质不是“把已经生成的 key 放进 cache”，而是：在编译期已知多个 bootstrapping target level 的前提下，把每个 `BK(r)` 拆成可验证的 key-material dependency graph，然后对 rotation key、linear-transform schedule、encoded diagonal、RNS-level view 做 canonical interning 与合法性验证，构造每个 target level 的 zero-copy 或 fallback view。你的约束明确要求使用同一 CKKS parameters、同一 secret key、同一 modulus chain、固定 target scale，并重点优化 rotation keys 与 bootstrapping linear transform keys；这正是 target-level-aware reusable bootstrap key planning，而不是普通 cache。

论文级 contribution 的边界是：提出“兼容性判定 + canonical ID + view construction + memory-aware scheduling + fallback correctness”的系统算法，并证明共享不会改变 CKKS/RNS-CKKS 语义；如果只做 `map[targetLevel] -> cachedKey`，没有贡献。

2. Assumptions and uncertainties

我基于 Lattigo v6.2.0 的公开 Go package 文档建模。Lattigo 的 CKKS package 是 RNS-accelerated CKKS，参数包括 ring dimension、ciphertext modulus chain、error variance、scale 等；文档也强调 modulus chain 与 default scale 会影响深度、精度、安全与性能。([Go Packages][1]) Lattigo bootstrapping evaluator 的 `OutputLevel()` 定义为 bootstrapping 后 ciphertext 的 level；集中式 bootstrapping 中它通常是 `MaxLevel - depth`。([Go Packages][2]) Lattigo v6 bootstrapping evaluation keys 包含 ring-switch keys、dense/sparse switch keys、relinearization key 和 Galois keys；其中 `MemEvaluationKeySet` 存储 relinearization key 与 Galois keys。([Go Packages][2])

关键 uncertainty 如下。

General CKKS concept: RNS level 是 ciphertext 当前使用的 `Q_0,...,Q_l` 模数前缀层级。
Lattigo Go implementation: `rlwe.Element` 有 `Level() / LevelQ() / LevelP()`；`ckks.Parameters` 有 `MaxLevel()`、`LogQLvl(level)`、`QLvl(level)` 等 level API。
Uncertainty: Lattigo evaluator 是否允许用高 level 的 evaluation key 在低 level ciphertext 上直接作为 prefix view，需要源码确认。
Required source-code check: `core/rlwe/evaluator_keyswitch.go`、`core/rlwe/keys.go`、`core/rlwe/gadget_product.go`，重点看 `GadgetProduct(levelQ, ...)` 是否只访问 `0..levelQ` limbs。

General CKKS concept: rotation key 是 automorphism 后的 key switching key。
Lattigo Go implementation: `GaloisKey` 内含 `GaloisElement`、`NthRoot` 和 `EvaluationKey`，用于 automorphism；Lattigo 说明其 automorphism 顺序与通常表述不同，会先对 `pi^{-1}` 的 GaloisKey 做 key switching 再应用 automorphism。([Go Packages][3])
Uncertainty: canonical ID 里应记录“用户 rotation k”还是 Lattigo 实际 `gal_el`。
Required source-code check: `schemes/ckks/evaluator_automorphism.go`、`core/rlwe/evaluator_automorphism.go`、`Parameters.GaloisElementForRotation(k)`。

General CKKS concept: bootstrapping linear transforms 是 CoeffsToSlots / SlotsToCoeffs 的 DFT/IDFT diagonal plaintexts。
Lattigo Go implementation: `dft.MatrixLiteral` 记录 `Type, LogSlots, LevelQ, LevelP, Levels, Format, Scaling, BitReversed, LogBSGSRatio`，其中 `LevelQ` 是 linear transform 起始 level，`LevelP` 必须和生成 Galois keys 时使用的 auxiliary primes 一致。([Go Packages][4])
Uncertainty: encoded diagonal 的底层 `LinearTransformation` 是否可被安全地按 RNS prefix zero-copy slice。
Required source-code check: `circuits/ckks/dft/dft.go`、`circuits/ckks/lintrans/lintrans.go`、`schemes/ckks/encoder.go`。

General CKKS concept: fixed target scale 只约束输出 scale，不自动保证 encoded plaintext 相同。
Lattigo Go implementation: plaintext encoding还依赖 `levelQ`、模数前缀、NTT/Montgomery domain、logSlots、encoding precision。
Uncertainty: 相同数学 diagonal、相同 scale、不同 level 的 encoded plaintext 是否能用高 level plaintext 的 limb prefix 表示。
Required source-code check: `ckks.Encoder.Encode`、`lintrans.Encode`、`rlwe.Plaintext` level metadata。

3. Bootstrap key decomposition

对每个 target level `r`，定义：

```text
BK(r) = SharedPart ∪ LevelSpecificPart(r)

BK(r) =
  RotationKeys(r)
  ∪ RelinearizationKeys(r)
  ∪ ConjugationKeys(r)
  ∪ LinearTransformKeys(r)
  ∪ GadgetDecompositionMaterial(r)
  ∪ ModulusChainMetadata(r)
  ∪ ScaleMetadata(r)
```

更精确地说，Lattigo v6 里“bootstrapping evaluation key”和“linear transform plaintext material”不完全是同一个对象。`bootstrapping.EvaluationKeys` 是 cryptographic evaluation key container；而 DFT/IDFT encoded matrices 存在 `Evaluator` 的 `S2CDFTMatrix`、`C2SDFTMatrix` 这类 matrix field 中。Lattigo 文档明确说 bootstrapping `Evaluator` 存储 plaintext matrices、polynomial approximation 和 keys。([Go Packages][2]) 所以本文把 `BK(r)` 扩展定义为“能执行 target-level bootstrapping 的全部 persistent material”，包括 cryptographic evaluation keys 与 encoded linear-transform plaintexts。

定义如下。

CKKS RNS level：ciphertext 当前处于 `Q[0:r]` 的 level，level 越高，可用 modulus limbs 越多。

Bootstrapping 后 target level：`Bootstrap(r)` 输出 ciphertext 的 RNS level。Lattigo 的 `OutputLevel()` 正是这个含义。([Go Packages][2])

Fixed target scale：所有 target level 输出 ciphertext 的 `Scale` 必须相同；允许 level 不同，不允许通过改变 scale 获得伪收益。

Rotation key：针对某个 Galois automorphism `gal_el` 的 `rlwe.GaloisKey`。它本质上是从 automorphed secret 回到原 secret 的 public key-switch material。([Go Packages][3])

Relinearization key：把 degree-2 ciphertext key-switched 回 degree-1 的 evaluation key。Lattigo 将 relinearization 与 automorphism 都建模为 `EvaluationKey` 应用场景。([Go Packages][3])

Conjugation key：CKKS conjugation 对应的特殊 Galois key。

Bootstrapping linear transform key：本文指 CoeffsToSlots / SlotsToCoeffs 的 encoded diagonal plaintext matrices；Lattigo 的 DFT matrix 由 `MatrixLiteral` 生成，`GenMatrices` 返回 DFT/IDFT 非零 diagonals 的有序 factor 列表。([Go Packages][4])

Modulus-chain-dependent key material：所有 `EvaluationKey` / `GaloisKey` / encoded plaintext diagonal 中依赖 `Q`、`P`、level、decomposition 的多项式数组。

Metadata-only material：target level、scale、matrix factorization schedule、rotation list、canonical IDs、compiler plan、serialization offsets 等。

核心结论：rotation keys 和 transform schedules 是最稳的共享对象；encoded diagonals 只有在 level/scale/modulus context 完全一致时才能直接共享；RNS slicing 是潜在强优化，但必须被源码和实验验证后才能成为 claim。

4.1 Rotation key sharing

如果不同 target level 的 bootstrapping linear transforms 使用相同 baby-step/giant-step rotation set，则 rotation keys 可以直接共享，前提是 Lattigo 实际 `gal_el`、secret key、params、`LevelQ/LevelP/BaseTwoDecomposition/compressed` 完全相同。Lattigo 的 `lintrans.GaloisElements` 和 `dft.MatrixLiteral.GaloisElements` 都提供 linear transform 所需 Galois elements。([Go Packages][5]) ([Go Packages][4])

如果 target level 只改变 linear transform 的执行 placement，而不改变 slot permutation，则 rotation key 仍可共享；slot permutation 决定 `gal_el`，不是 target level 本身。

如果 target level 改变导致 key switching level、modulus prefix、`LevelP` 或 decomposition 参数不同，则不能直接声称共享。可以有三种策略：第一，exact match 共享；第二，生成高 level superset key 并让低 level 操作引用同一 key；第三，zero-copy RNS slice view。第二、第三都必须验证 Lattigo evaluator 是否合法接受。

Lattigo 的 `EvaluationKeyParameters` 显式含有 `LevelQ, LevelP, BaseTwoDecomposition, Compressed`，说明 key material 与这些参数绑定。([Go Packages][3]) 因此 canonical rotation-key pool 应定义为：

```text
RotationKeyID =
  H(
    "RotationKey",
    secret_key_id,
    optional_ephemeral_or_domain_key_id,
    params_id,
    gal_el,
    ring_type,
    logN,
    nth_root,
    evk_levelQ,
    evk_levelP,
    base_two_decomposition,
    compressed,
    key_domain_in,
    key_domain_out
  )
```

然后每个 `BK(r)` 不持有 key 副本，只持有 `RotationKeyID` view。

4.2 Bootstrapping linear transform key sharing

结论：

```text
Can share rotation structure?
Yes, if GaloisElements sets are identical or overlapping.

Can share encoded plaintext diagonals?
Only if mathematical diagonal values, scale, LevelQ, modulus prefix, logSlots,
encoding precision, NTT/Montgomery domain, and transform format are identical.

Can share transform schedule?
Yes, if factorization and BSGS parameters are identical.

Can share memory layout?
Yes for metadata and possibly encoded arrays if exact-compatible.
RNS-prefix view is UNKNOWN until verified.

Can share only metadata?
Always, for matrix literals, schedule IDs, diagonal value hashes, and serialization offsets.
```

Lattigo `dft.MatrixLiteral` 的 `LevelQ` 是 linear transform 起始 level，`LevelP` 是 automorphism 使用的 auxiliary primes 数量，并要求用户保证它和 Galois keys 使用的值相同。([Go Packages][4]) 这直接说明：encoded diagonal 不是只由数学矩阵决定，还和执行 level 绑定。

所以判断规则是：

```text
same mathematical matrix + same rotation set
  => share schedule and rotation keys

same mathematical matrix + same scale + same LevelQ + same modulus context
  => share encoded diagonals

same mathematical matrix + same scale but different LevelQ
  => share abstract diagonals/schedule; re-encode or validated RNS view
```

固定 target scale 是必要条件，不是充分条件。

4.3 RNS limb slice / modulus-chain sharing

理论上，RNS material 常常可以被看作 `Q[0:L]` 的前缀对象；如果较低 target level 只需要 `Q[0:r]`，而高 level key 已含有 `Q[0:R]`，则可能构造 prefix view。Lattigo `Element` 支持 level metadata，`LevelQ()` / `LevelP()` 存在，`NewElementAtLevelFromPoly` 文档还明确说返回对象会共享传入 polynomial 的 backing array。([Go Packages][3]) 这说明 zero-copy view 在 Lattigo 数据结构层面可能可行。

但对 key-switch key 不能直接下结论。原因是 `EvaluationKey` 内部是 `GadgetCiphertext`；其 decomposition vector size 可能依赖 `levelQ, levelP, baseTwoDecomposition`。Lattigo 的 `GadgetCiphertext` 有 `LevelQ()`、`LevelP()`、`BaseRNSDecompositionVectorSize()`、`BaseTwoDecompositionVectorSize()` 等 API，意味着 slicing 不只是切掉 modulus limb，还可能涉及 gadget decomposition 布局。([Go Packages][3])

因此：

```text
Can generate highest-level key then use as lower-level key?
Status: UNKNOWN until source and tests confirm.

If Lattigo evaluator only reads required prefix limbs:
  legal as superset-key view.

If evaluator requires exact LevelQ in key metadata:
  implement zero-copy wrapper or fallback exact key.

If gadget decomposition layout changes with level:
  no safe slicing; only share keygen schedule/intermediate abstract specs.
```

这套系统必须把 RNS slice 标为 optional optimization，不应作为无验证主 claim。

4.4 Lazy / on-demand generation

这里不是 runtime lazy。理由很简单：keygen 需要 secret key，耗时长，内存峰值高，不应在 evaluator 的在线路径中突然触发。正确做法是 compile-time demand-driven generation：

```text
compiler emits BootstrapUse(targetLevel=r, transformSpec, rotationSet)
planner computes only actually reachable target levels
keygen stage generates union/intersection-optimized material
runtime receives immutable SharedKeyPool + TargetLevelKeyViews
```

这样可以直接消除未使用 target levels 的 keygen、persistent storage 和 runtime RAM；这也是你要求的 baseline 消融 A1。

5. Core algorithm

Algorithm name:

```text
Target-Level-Aware Bootstrap Key Sharing Planner
```

输入：

```text
TargetLevels
CKKSParams
LattigoBootstrapParams
FixedTargetScale
SecretKeyID
RotationSets[r]
LinearTransformSpecs[r]
MemoryBudget
KeyGenerationCostModel
PersistentStorageBudget
RuntimeRAMBudget
```

输出：

```text
ReusableBootstrapKeyPlan
SharedKeyPool
TargetLevelKeyViews
GenerationSchedule
CachePolicy
ValidationReport
```

核心思想是把每个 target level 的需求写成 dependency graph：

```text
TargetLevel r
 ├── BootstrappingProfile(r)
 │    ├── OutputLevel r
 │    ├── FixedTargetScale
 │    ├── CircuitOrder
 │    ├── Mod1 parameters
 │    ├── CoeffsToSlots specs
 │    └── SlotsToCoeffs specs
 ├── Cryptographic keys
 │    ├── RelinearizationKeyID
 │    ├── RotationKeyID[gal_el]
 │    ├── ConjugationKeyID
 │    ├── RingSwitchKeyID
 │    └── DenseSparseSwitchKeyID
 └── Linear transform material
      ├── TransformScheduleID
      ├── AbstractDiagonalID
      └── EncodedDiagonalID
```

Planner 的策略：

第一，先做 exact interning。只要 canonical ID 完全相同，就复用同一对象。

第二，对 rotation keys 做 overlap grouping。对每个 `gal_el`，比较不同 target level 的 `EvaluationKeyParameters`。完全相同则共享；level 不同则进入 superset/slice feasibility 判断。

第三，对 linear transform 拆成三层共享：schedule、abstract diagonal、encoded diagonal。schedule 共享最宽，encoded diagonal 共享最窄。

第四，RNS-level slice 只在 `CanSliceKeyMaterial = TRUE` 时启用；`UNKNOWN` 时只允许实验开关，不进入默认生产路径。

第五，在 memory budget 下选择 exact-key 还是 superset-key。superset-key 可能减少 keygen time 和 key 数量，但可能增加 persistent size 与 runtime RAM；exact-key 反之。

第六，构造 `TargetLevelKeyView`。view 只存 ID、指针和 level metadata，不复制 key material。

第七，任何兼容性判定失败或 unknown 且无实验许可时，fallback 到 full key generation for that target level。

6. Pseudocode

```python
UNKNOWN = "UNKNOWN"
TRUE = "TRUE"
FALSE = "FALSE"
VIEW = "VIEW"
EXACT = "EXACT"
FALLBACK = "FALLBACK"

class Node:
    def __init__(self, id, kind, attrs):
        self.id = id
        self.kind = kind
        self.attrs = attrs
        self.deps = set()

class Graph:
    def __init__(self):
        self.nodes = {}
        self.edges = []

    def add(self, node):
        self.nodes[node.id] = node
        return node.id

    def dep(self, parent, child):
        self.nodes[parent].deps.add(child)
        self.edges.append((parent, child))


def BuildDependencyGraph(TargetLevels):
    """
    Input:
      TargetLevels, CKKSParams, FixedTargetScale, RotationSets[r],
      LinearTransformSpecs[r], LattigoBootstrapParams
    Output:
      graph
    """
    graph = Graph()

    params_id = HashParams(CKKSParams)
    scale_id = HashScale(FixedTargetScale)

    for r in TargetLevels:
        target_id = H("TargetLevel", r, params_id, scale_id)
        graph.add(Node(target_id, "TargetLevel", {
            "level": r,
            "params_id": params_id,
            "scale_id": scale_id
        }))

        profile_id = H("BootstrapProfile", r, params_id, LattigoBootstrapParams.digest())
        graph.add(Node(profile_id, "BootstrapProfile", {
            "target_level": r,
            "btp": LattigoBootstrapParams.for_level(r),
            "fixed_scale": FixedTargetScale
        }))
        graph.dep(target_id, profile_id)

        relin_id = H("RelinearizationKey",
                     SecretKeyID, params_id,
                     RequiredRelinKeyParams(r))
        graph.add(Node(relin_id, "RelinearizationKey", {
            "sk": SecretKeyID,
            "params_id": params_id,
            "evk_params": RequiredRelinKeyParams(r)
        }))
        graph.dep(target_id, relin_id)

        for gal_el in RotationSets[r]:
            rot_id = CanonicalizeRotationKey(
                gal_el=gal_el,
                params=CKKSParams,
                level=RequiredKeyLevel(r, gal_el),
                decomposition=RequiredDecomposition(r, gal_el)
            )
            if rot_id == UNKNOWN:
                rot_id = H("FullFallbackRotationKey", r, gal_el)
            graph.add(Node(rot_id, "RotationKey", {
                "gal_el": gal_el,
                "target_level": r
            }))
            graph.dep(target_id, rot_id)

        for spec in LinearTransformSpecs[r]:
            lt = CanonicalizeLinearTransform(
                spec=spec,
                level=spec.LevelQ,
                scale=FixedTargetScale,
                params=CKKSParams
            )
            graph.add(Node(lt["schedule_id"], "TransformSchedule", lt["schedule_attrs"]))
            graph.dep(target_id, lt["schedule_id"])

            for diag_id, diag_attrs in lt["encoded_diagonal_ids"]:
                graph.add(Node(diag_id, "EncodedDiagonal", diag_attrs))
                graph.dep(target_id, diag_id)

    return graph


def CanonicalizeRotationKey(gal_el, params, level, decomposition):
    """
    Output:
      RotationKeyID or UNKNOWN
    """
    if gal_el is None or params is None:
        return UNKNOWN

    params_id = HashParams(params)
    evk_params = {
        "LevelQ": level.LevelQ,
        "LevelP": level.LevelP,
        "BaseTwoDecomposition": decomposition.BaseTwo,
        "Compressed": decomposition.Compressed
    }

    if evk_params["LevelQ"] is None or evk_params["LevelP"] is None:
        return UNKNOWN

    return H("RotationKey",
             SecretKeyID,
             params_id,
             int(gal_el),
             params.LogN,
             params.RingType,
             evk_params)


def CanonicalizeLinearTransform(spec, level, scale, params):
    """
    Output:
      {
        schedule_id,
        schedule_attrs,
        encoded_diagonal_ids
      }
    """
    if spec is None:
        return UNKNOWN

    params_id = HashParams(params)

    schedule_attrs = {
        "Type": spec.Type,
        "LogSlots": spec.LogSlots,
        "Levels": tuple(spec.Levels),
        "Format": spec.Format,
        "BitReversed": spec.BitReversed,
        "LogBSGSRatio": spec.LogBSGSRatio,
        "DiagonalPatternHash": H(spec.NonZeroDiagonalIndexes)
    }

    schedule_id = H("TransformSchedule", schedule_attrs)

    encoded_ids = []
    for diag in spec.Diagonals:
        value_hash = H("DiagonalValues", diag.index, diag.values)
        attrs = {
            "params_id": params_id,
            "diag_index": diag.index,
            "value_hash": value_hash,
            "LevelQ": level,
            "LevelP": spec.LevelP,
            "scale": scale,
            "logSlots": spec.LogSlots,
            "format": spec.Format,
            "encoding_precision": spec.EncodingPrecision,
            "domain": "NTT/Montgomery"
        }
        diag_id = H("EncodedDiagonal", attrs)
        encoded_ids.append((diag_id, attrs))

    return {
        "schedule_id": schedule_id,
        "schedule_attrs": schedule_attrs,
        "encoded_diagonal_ids": encoded_ids
    }


def CanShareRotationKey(key_a, key_b):
    """
    Input:
      canonical key descriptors
    Output:
      TRUE, VIEW, FALSE, or UNKNOWN
    """
    fields = ["gal_el", "secret_key_id", "params_id",
              "ring_type", "logN", "key_domain_in", "key_domain_out",
              "BaseTwoDecomposition", "Compressed"]

    for f in fields:
        if key_a.get(f) != key_b.get(f):
            return FALSE

    if key_a["LevelQ"] == key_b["LevelQ"] and key_a["LevelP"] == key_b["LevelP"]:
        return TRUE

    larger, smaller = PickSupersetCandidate(key_a, key_b)
    status = CanSliceKeyMaterial(larger, smaller["LevelQ"])

    if status == TRUE:
        return VIEW
    if status == UNKNOWN:
        return UNKNOWN
    return FALSE


def CanShareEncodedDiagonal(diag_a, diag_b):
    """
    Output:
      TRUE, VIEW, FALSE, or UNKNOWN
    """
    exact_fields = ["params_id", "diag_index", "value_hash",
                    "scale", "logSlots", "format",
                    "encoding_precision", "domain"]

    for f in exact_fields:
        if diag_a.get(f) != diag_b.get(f):
            return FALSE

    if diag_a["LevelQ"] == diag_b["LevelQ"] and diag_a["LevelP"] == diag_b["LevelP"]:
        return TRUE

    if SameModulusPrefix(diag_a, diag_b):
        return UNKNOWN  # possible RNS-prefix plaintext view, but not safe by default

    return FALSE


def CanSliceKeyMaterial(superset_key, required_level):
    """
    Output:
      TRUE, FALSE, or UNKNOWN
    """
    if superset_key["LevelQ"] < required_level.LevelQ:
        return FALSE

    if superset_key["LevelP"] != required_level.LevelP:
        return FALSE

    if superset_key["BaseTwoDecomposition"] != required_level.BaseTwoDecomposition:
        return FALSE

    if superset_key.get("Compressed", False):
        return UNKNOWN  # compressed key expansion may allocate exact layout

    if not SourceValidationFlag("GadgetCiphertextPrefixViewLegal"):
        return UNKNOWN

    if not TestValidationFlag("ExactKeyVsSlicedKeyEquivalent"):
        return UNKNOWN

    return TRUE


def BuildSharedKeyPool(graph):
    """
    Output:
      shared_pool with interned exact objects and optional view groups
    """
    pool = SharedKeyPool()

    groups = GroupByCanonicalCompatibility(graph.nodes)

    for group in groups:
        exact_buckets = InternByExactID(group)

        for exact_id, nodes in exact_buckets.items():
            pool.add_exact(exact_id, nodes[0])

        cross_level_groups = GroupByIgnoringLevel(group)
        for g in cross_level_groups:
            best = ChooseSupersetOrExact(g)
            if best.status == TRUE:
                pool.add_superset(best.superset_id, best.members)
            elif best.status == UNKNOWN:
                pool.mark_requires_validation(g)
                pool.add_exact_all(g)  # safe fallback
            else:
                pool.add_exact_all(g)

    return pool


def BuildTargetLevelViews(shared_pool, TargetLevels):
    """
    Output:
      map[targetLevel]BootstrapKeyView
    """
    views = {}

    for r in TargetLevels:
        view = BootstrapKeyView(target_level=r)

        for req in RequiredMaterialsForTarget(r):
            material = shared_pool.resolve(req)

            if material is None:
                view.status = FALLBACK
                view.fallback_reason.append(("missing", req))
                continue

            if material.kind == "Superset":
                slice_status = CanSliceKeyMaterial(material.descriptor, req.level)
                if slice_status == TRUE:
                    view.add_zero_copy_view(req, material)
                elif slice_status == UNKNOWN:
                    view.status = FALLBACK
                    view.fallback_reason.append(("slice_unknown", req))
                else:
                    view.status = FALLBACK
                    view.fallback_reason.append(("slice_illegal", req))
            else:
                view.add_exact(req, material)

        views[r] = view

    return views


def OptimizeGenerationSchedule(shared_pool, cost_model, memory_budget):
    """
    Output:
      generation schedule minimizing keygen time, persistent size, and peak RAM heuristically
    """
    schedule = []

    materials = shared_pool.materials()
    materials.sort(key=lambda m: (
        -m.reuse_count,
        m.estimated_size,
        m.kind
    ))

    live_memory = 0
    for m in materials:
        if live_memory + cost_model.peak_keygen_ram(m) > memory_budget:
            schedule.append(("flush_and_release_buffers",))
            live_memory = shared_pool.persistent_live_size()

        schedule.append(("generate", m.id))
        live_memory += cost_model.peak_keygen_ram(m)

        if m.persist_immediately:
            schedule.append(("serialize", m.id))
            schedule.append(("release_intermediate", m.id))
            live_memory -= cost_model.intermediate_ram(m)

    return KeyGenerationSchedule(schedule)


def ValidatePlan(plan):
    """
    Output:
      ValidationReport
    """
    report = ValidationReport()

    for r, view in plan.TargetLevelKeyViews.items():
        if view.status == FALLBACK:
            report.add_warning(r, "fallback_full_generation_required", view.fallback_reason)
            continue

        if not view.has_all_required_materials():
            report.add_error(r, "missing_required_material")
            continue

        if view.fixed_scale != FixedTargetScale:
            report.add_error(r, "scale_policy_violation")

        if not SameParams(view.params, CKKSParams):
            report.add_error(r, "params_mismatch")

        for diag in view.encoded_diagonals:
            if diag.shared:
                if CanShareEncodedDiagonal(diag.source, diag.target) not in [TRUE, VIEW]:
                    report.add_error(r, "illegal_diagonal_sharing")

        for key in view.rotation_keys:
            if key.shared:
                status = CanShareRotationKey(key.source, key.target)
                if status not in [TRUE, VIEW]:
                    report.add_error(r, "illegal_rotation_key_sharing")
                if status == UNKNOWN:
                    report.add_warning(r, "rotation_key_requires_validation")

        report.add_test(r, "bootstrap_random_plaintexts")
        report.add_test(r, "output_level_equals_target")
        report.add_test(r, "output_scale_equals_fixed_scale")
        report.add_test(r, "precision_not_worse_than_baseline")

    if report.has_error():
        plan.force_full_key_fallback_for_errors()

    return report
```

7. Optimization model

令 `R` 是 target levels 集合，`U_r` 是 target level `r` 需要的 key/material universe。候选 material 集合 `C` 包括 exact key、superset key、RNS view、encoded diagonal、abstract diagonal、schedule 等。

变量：

```text
x_c ∈ {0,1}: 是否生成候选 material c
y_{r,c} ∈ {0,1}: target level r 是否使用 material c
v_{r,c} ∈ {0,1}: 是否使用 c 的 view/slice
s_{c,t} ∈ {0,1}: generation schedule 中 c 是否在时刻 t live
```

目标：

```text
minimize
  Σ_c keygen_time(c) * x_c
  + λ1 * Σ_c persistent_size(c) * x_c
  + λ2 * peak_t Σ_c runtime_ram(c) * live_{c,t}
  + λ3 * Σ_{r,c} latency_overhead(r,c) * y_{r,c}
```

约束：

```text
for every r and every required item u ∈ U_r:
  Σ_{c covers u} y_{r,c} ≥ 1

y_{r,c} ≤ x_c

fixed target scale preserved:
  scale(output(r)) = FixedTargetScale

same CKKS params:
  params(c) = CKKSParams for all cryptographic c

same secret key:
  sk_domain(c) compatible with SecretKeyID and ephemeral policy

security unchanged:
  LogN, Q, P, secret distribution not weakened

memory:
  persistent_size(plan) ≤ PersistentStorageBudget
  peak_keygen_RAM(schedule) ≤ MemoryBudget
  peak_runtime_RAM(view execution) ≤ RuntimeRAMBudget

if v_{r,c}=1 and c is RNS slice:
  CanSliceKeyMaterial(c, required_level(r)) = TRUE

if encoded diagonal shared:
  CanShareEncodedDiagonal(source, target) = TRUE

if UNKNOWN:
  either experimental mode with validation proof
  or y_{r,c}=0 and fallback exact/full key is used
```

这个优化问题本质上是 weighted set cover + DAG scheduling + compatibility-constrained ILP。set cover 负责选择哪些 shared/superset materials 覆盖 target requirements；DAG scheduling 负责 keygen 顺序和峰值内存；ILP 是精确形式。工程上不需要求全局最优，使用 greedy + validation 足够：

```text
1. exact canonical interning: O(total_materials)
2. rotation-key overlap greedy: 按 saved_size / added_cost 选择 superset
3. linear-transform schedule exact interning
4. encoded diagonal exact sharing only
5. optional RNS slicing only after validation
6. memory-aware topological generation
```

这比普通 cache 强，因为它在生成之前就改变了 keygen universe，而不是生成之后去重。

8. Correctness argument

命题 1：每个 `TargetLevelKeyView(r)` 包含完整 required key material。
证明思路：`BuildDependencyGraph` 对每个 target level 枚举所有 required rotation keys、relinearization key、conjugation key、ring-switch key、dense/sparse key、linear transform schedule 和 encoded diagonals。`BuildTargetLevelViews` 对每个 required item 做 `resolve`；若缺失则标记 fallback。`ValidatePlan` 在无错误时保证每个 required item 被 exact material 或合法 view 覆盖。

命题 2：共享 rotation key 不改变 automorphism / key switching 语义。
证明思路：Lattigo `GaloisKey` 是针对具体 `GaloisElement` 的 automorphism key-switch material。只要 `gal_el`、`skIn/skOut`、params、level/decomposition 完全相同，共享对象和复制对象在 evaluator 看到的是同一 public key-switch ciphertext；使用次数不会改变它的数学含义。Lattigo 文档也说明 GaloisKey 用于将 automorphism 后的 secret 重新切换回原 secret。([Go Packages][3])

命题 3：共享 encoded diagonal 不改变 linear transform。
证明思路：encoded diagonal 共享必须满足数学值、scale、level、modulus context、logSlots、format、encoding precision 全相同。因此 evaluator 执行的 plaintext-ciphertext multiplication 序列逐项相同。若任一字段不同，planner 不共享 encoded diagonal，只共享 schedule 或 abstract diagonal。

命题 4：RNS slice view 正确性。
证明思路：只有当 `CanSliceKeyMaterial=TRUE` 时启用。TRUE 的含义不是“猜测”，而是源码确认 evaluator 只读取 required prefix limbs，并且实验确认 exact key 与 sliced/superset key 在所有 target levels 上通过 bootstrap correctness、output level、output scale 和 precision tests。否则 fallback。

命题 5：fallback full generation 保证不会产生错误 key。
证明思路：任何 `UNKNOWN/FALSE` 的共享判定都会触发 exact generation 或 full-key-per-target fallback。该 fallback 与 baseline 完全一致，因此不会比 baseline 更不正确。

9. Security analysis

Safe under same params and same secret key:

复用 evaluation key 不改变 secret key 分布，不改变 `LogN`、`Q/P`、error distribution、secret distribution，也不改变 CKKS plaintext scale policy。因此在相同 CKKS params、相同 secret-key domain、相同 evaluation-key parameter 下，共享 key material view 不需要重新运行 security estimator。Lattigo 文档说明 CKKS 安全与 ring dimension、ciphertext modulus、error variance等参数强相关；只要这些不变，复用对象本身不是新参数。([Go Packages][1])

多 target level 共享 key material 不引入比 baseline 更多的 evaluation-key samples。事实上，若 baseline 为每个 target 生成一套 key，反而会生成更多 public evaluation-key ciphertexts。共享减少样本数量，通常不会增加 leakage。标准边界是：evaluation keys 是 public auxiliary keys，可被重复使用；安全假设允许多次 evaluation 使用相同 public evaluation keys。

Requires validation:

如果 Lattigo bootstrapping 使用 ephemeral sparse secret，则必须把 ephemeral secret 视为 key domain 的一部分。Lattigo `GenEvaluationKeys` 文档说明 bootstrapping evaluation keys 在 ephemeral secret `skN2` 下生成，并返回该 ephemeral key 用于 debugging；同时提醒 bootstrapping parameters 有独立 cryptographic parameters，用户需要确保其满足目标安全。([Go Packages][2]) 因此共享计划必须固定 ephemeral secret policy：要么 `EphemeralSecretWeight=0`，要么显式生成一个 canonical ephemeral secret，并把 `ephemeral_secret_id` 写入 key ID。

如果 superset key 使用比 exact target 更大的 `LevelQ` 或更多 auxiliary primes `P`，虽然用户约束说 modulus chain 相同，但 persistent material 暴露更多 public samples。通常这仍在同一参数安全模型内，但如果它改变了实际使用的 `logQP` 或 secret distribution，就必须重新估计安全。

Unsafe / not allowed:

不允许为节省内存减少必要 rotation set。不允许降低 `LogN`、减少安全要求下必要的 modulus、改变 secret distribution、改变 target scale、改变 bootstrapping 数学电路来伪造收益。不允许在 `CanShareEncodedDiagonal=FALSE` 时共享 encoded diagonal。不允许在 `CanSliceKeyMaterial=UNKNOWN` 时默认启用 slicing。

建议模块如下。

```go
type KeyMaterialID struct {

}

```

职责说明：

`KeyMaterialID` 是所有 material 的 canonical identity。它必须可序列化，并参与 persistent storage。

`RotationKeyID` 是 Galois key 的强 ID。它必须包含 `gal_el` 和 evk 参数，因为 Lattigo `GaloisKey` 是 `GaloisElement + EvaluationKey`。([Go Packages][3])

`LinearTransformID` 只描述 schedule，不等于 encoded diagonal。它可以大量共享，几乎总是 metadata-only。

`EncodedDiagonalID` 描述真正占内存的 encoded plaintext diagonal。只有 exact-compatible 才能共享。

`BootstrapKeyView` 是 target-level runtime 入口。它不拥有大对象，只引用 `SharedKeyPool`。它需要能构造 Lattigo 原生 `bootstrapping.EvaluationKeys`，因为 Lattigo `NewEvaluator(btpParams, evk)` 接收 `*EvaluationKeys`。([Go Packages][2])

`SharedKeyPool` 持有原生 Lattigo objects。rotation/relin/evaluation keys 参与 persistent storage；transform schedule 可只存 metadata；encoded diagonals 若大则应序列化并按 runtime demand 加载。

`KeyGenerationSchedule` 控制 keygen RAM。生成一个大对象后立即 serialize，释放临时 buffers，避免 peak RAM 爆炸。

`PlanValidator` 是论文系统的核心防线。任何 RNS slicing、encoded diagonal view、superset key view 都必须经过它。

与 Lattigo 原生 key/evaluator 的关系：本系统不修改底层 CKKS 算法；它在 Lattigo 上层构造 `EvaluationKeys` 和 matrices 的共享 view。Lattigo 的 `EvaluationKeySet` 接口要求能取 Galois key 和 relinearization key，并且实现需并发安全；因此自定义 `SharedEvaluationKeySet` 可以是一个合法 extension point。([Go Packages][3])

12. Paper contribution framing

贡献点 1：Target-level-aware bootstrap key planning。

它解决的问题是：多 target level bootstrapping 的 key material 不是独立集合，而是高度重叠的 dependency graph。它不是普通 cache，因为 planner 在 keygen 前决定哪些 material 被生成、哪些被 view 引用、哪些 fallback。它与 target-level planning 强相关，因为不同 target level 会改变 level placement、encoded diagonal context、possibly decomposition 参数。实验支撑：A0 vs A1-A5，展示 target 数量和 overlap ratio 对收益的影响。薄弱点：如果 target levels 很少或 rotation overlap 很低，收益不足。

贡献点 2：Canonical key material interning for CKKS bootstrapping。

它解决的问题是：rotation keys、relinearization keys、ring-switch keys、encoded diagonals 的兼容性边界不同。本文给出不同对象的 canonical ID 和 safe-sharing predicate。它不是普通 cache，因为 ID 包含 cryptographic domain、Galois element、level、decomposition、scale、modulus context，并由 validator 强制执行。实验支撑：错误注入测试，例如故意改变 LevelQ、LevelP、scale，验证 validator 拒绝共享。薄弱点：需要说明 Lattigo-specific 部分如何泛化到 OpenFHE/SEAL。

贡献点 3：Compiler-guided demand-driven key generation with memory-aware key views。

它解决的问题是：FHE 编译器知道哪些 bootstrapping target levels 真正会出现，但传统 keygen 不利用这点。它不是普通 cache，因为它把 compiler plan 编译成 keygen DAG 和 runtime view，而不是 runtime 中被动查找。实验支撑：真实 HE workload，如 encrypted inference graph，统计 unused target levels、peak keygen RAM、runtime RAM。薄弱点：必须证明强于“A1 only demand-driven generation”这个简单 baseline。

13. Reviewer-style vulnerability audit

14. 这是否只是普通 key cache？

Risk: 被审稿人认为只是 dedup map。
Why it matters: 普通 cache 不够论文贡献。
How to validate: 展示 keygen 前 dependency graph、compatibility predicate、superset/exact 选择、fallback proof。
Possible fix: 把核心贡献表述为 planning + compatibility verification + view construction。
Impact on contribution: 若只有 cache，贡献弱；若有 formal planner，贡献成立。

2. 这是否依赖 Lattigo Go 的偶然实现，泛化性不足？

Risk: Lattigo-specific structs 太多。
Why it matters: 系统论文需要泛化。
How to validate: 把抽象层分为 CKKS-general 和 Lattigo adapter。
Possible fix: canonical IDs 用 general fields；Lattigo 只作为 backend。
Impact on contribution: 泛化后更强。

3. 是否错误假设不同 target level 的 bootstrapping keys 可以复用？

Risk: 某些 key/diagonal 确实 level-specific。
Why it matters: 错误共享会破坏 correctness。
How to validate: 每类 material 有独立 `CanShare` predicate。
Possible fix: encoded diagonals 默认 exact-only；RNS slice 默认 off。
Impact on contribution: rotation/schedule sharing 仍成立。

4. 是否节省 storage 但增加 bootstrap latency？

Risk: superset key 或 unified high-level bootstrap 可能更慢。
Why it matters: 系统优化不能只看 storage。
How to validate: 记录 latency_overhead 项。
Possible fix: optimization objective 加 `λ3 * latency`；必要时 exact-key。
Impact on contribution: 变成 Pareto planner，而非单目标压缩。

5. 是否节省 persistent size 但增加 runtime RAM？

Risk: pool 一次加载所有共享 key 导致 RAM 爆炸。
Why it matters: 用户目标包含 runtime peak RAM。
How to validate: runtime key material reference count 和 LRU loading。
Possible fix: cache policy 按 target-level execution window 加载/卸载。
Impact on contribution: 加入 runtime scheduler 后更强。

6. key slicing 是否在 Lattigo 的 RNS key format 下真的合法？

Risk: gadget decomposition 布局不支持 prefix view。
Why it matters: 这是最危险 claim。
How to validate: 源码审计 + exact/slice equivalence tests。
Possible fix: slicing 作为 optional A5，不作为主收益。
Impact on contribution: 若失败，rotation exact interning 仍可发表；A5 变 future work。

7. encoded plaintext diagonals 是否因为 level/scale/context 不同而无法共享？

Risk: 大量 target level 的 encoded diagonals 不兼容。
Why it matters: 用户重点之一是 linear transform keys。
How to validate: 统计 encoded-diagonal compatibility ratio。
Possible fix: 共享 abstract diagonals 和 schedule，按 level lazy re-encode。
Impact on contribution: storage savings 下降，但 keygen/schedule simplification 仍有价值。

8. target scale 固定是否足以保证 diagonal sharing？

Risk: 不足。
Why it matters: 这是常见错误。
How to validate: 改变 LevelQ，保持 scale，比较 encoded plaintext hash。
Possible fix: sharing predicate 必须包含 level 和 modulus prefix。
Impact on contribution: 明确这一点反而增强可信度。

9. 是否需要 security re-estimation？

Risk: 如果 superset 改变 logQP 或 secret distribution，需要重估。
Why it matters: 安全 claim 高风险。
How to validate: 检查 `LogN, Q, P, secret distribution, ephemeral weight` 是否完全相同。
Possible fix: 只在同参数同 secret 下声明安全；其他情况要求 estimator。
Impact on contribution: 不影响同参数场景。

10. 是否有可能 keygen time 没减少，只是 storage 减少？

Risk: 如果仍然先生成再 dedup，keygen 不减少。
Why it matters: 用户目标包含 keygen time。
How to validate: 统计 generated material count，不是 only serialized size。
Possible fix: planner 必须在 generation 前 intern。
Impact on contribution: 这是区分普通 cache 的关键。

11. 是否 target levels 数量少时收益不足？

Risk: k=1 或 k=2 时收益不明显。
Why it matters: 实验可能被质疑 cherry-pick。
How to validate: sweep target level count。
Possible fix: 明确收益条件：multi-target + high rotation overlap。
Impact on contribution: 限定适用范围即可。

12. 是否实验 workload 选择会夸大收益？

Risk: 只选 rotation overlap 很高的 workload。
Why it matters: 系统论文审稿常见攻击点。
How to validate: report overlap ratio and include low/medium/high overlap workloads。
Possible fix: synthetic + real workloads 双轨实验。
Impact on contribution: 实验更可信。

13. 是否真正优于“只生成 compiler-used target levels”的简单 baseline？

Risk: A1 已经解决大量浪费。
Why it matters: 必须证明 A2-A5 的增量。
How to validate: ablation A1 vs A2/A3/A4/A5。
Possible fix: 把 strongest claim 放在 rotation-key interning 和 transform schedule/diagonal compatibility，而不是 demand-only。
Impact on contribution: 若 A2-A5 没明显收益，论文贡献变弱。

14. Final verdict

Is this publishable as an algorithm/system contribution?

可以，但最强版本不是“key cache”，而是“compiler-guided, target-level-aware bootstrap key material planner with verified sharing predicates and runtime key views”。如果实验证明 rotation-set overlap 在真实 workload 中高，并且 A2/A3/A4 明显优于 A1，这可以作为系统/编译器方向的可发表贡献。

What is the strongest version of the contribution?

最强表述是：

```text
We model multi-target-level CKKS bootstrapping key generation as a
compatibility-constrained material-cover and memory-aware scheduling problem,
and implement a Lattigo-backed planner that constructs shared key pools and
target-level views with formal fallback correctness.
```

实际核心收益排序预计是：

```text
1. compile-time demand-driven generation
2. rotation-key interning
3. linear-transform schedule interning
4. exact-compatible encoded diagonal sharing
5. verified RNS slice / superset view
```

What must be verified in Lattigo source before claiming it?

必须检查：

```text
core/rlwe/keys.go
core/rlwe/evaluator_keyswitch.go
core/rlwe/evaluator_automorphism.go
core/rlwe/gadget_product.go
schemes/ckks/evaluator.go
circuits/ckks/bootstrapping/keys.go
circuits/ckks/bootstrapping/evaluator.go
circuits/ckks/dft/dft.go
circuits/ckks/lintrans/lintrans.go
```

必须确认：

```text
1. GaloisKey lookup uses exact gal_el expected by planner.
2. EvaluationKeyParameters LevelQ/LevelP/BaseTwoDecomposition semantics.
3. Higher-LevelQ key can or cannot be used at lower ciphertext level.
4. GadgetCiphertext layout supports or rejects prefix view.
5. Encoded linear transformation plaintexts can or cannot share RNS backing arrays.
6. Bootstrapping evaluator output level and scale are exactly checked.
7. Ephemeral secret generation policy is controlled and reproducible.
```

最终结论：默认可安全发布的方案是 A1+A2+A3+A4-exact；A5 RNS slicing 只有在 Lattigo source 和 equivalence tests 都通过后才能作为正式贡献，否则应标为 optional/future optimization。
